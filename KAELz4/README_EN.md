
# KAELz4 Asynchronous Compression API User Guide

## 1. API Overview

In modern computing environments, data compression is a key method for improving data transmission efficiency and saving storage space. However, conventional compression methods are usually executed synchronously, which may cause performance bottlenecks when processing large-volume data, especially under heavy loads. To better leverage the capabilities of hardware accelerators and accelerate the system response, we have developed the KAELz4 asynchronous compression APIs.

These APIs are designed for high-concurrency and large-volume data compression. By introducing concurrent threads to compress data, they can fully utilize the parallel computing capability of modern multi-core CPUs, and further improve the compression speed with the support of the hardware accelerator KAE.

### Features

* Asynchronous compression: Compression runs asynchronously without blocking the main thread. Results are returned via callback upon completion.
* Hardware-based acceleration: The hardware accelerator boosts compression speed, while APIs enhance compression task efficiency and reduce CPU load.
* Multi-thread concurrency: Tasks are distributed evenly through multi-thread intelligent scheduling, further improving the overall performance. In dual-accelerator environments, cores are automatically and evenly distributed across both accelerators, balancing workloads and optimizing resource utilization.
* LZ4 compatibility: The compressed data generated by these APIs is compatible with the LZ4 format used in the community.
* Easy integration: The APIs can be easily integrated into existing applications. By simply calling APIs and providing callbacks, you can quickly start asynchronous compression and implement high-performance data compression.

### Application Scenarios

* High-concurrency and heavy-load scenarios: When handling numerous simultaneous data compression tasks, the APIs support multi-thread execution to prevent single-thread blocking and enhance system responsiveness.
* Low-latency scenarios: For systems that require low latency and quick response, the APIs can maintain smooth operation by avoiding blocking the main thread. For example, for real-time data transmission, distributed storage, or streaming media processing, they can effectively prevent frame freezing during data compression.

## 3. API Function Signature and Parameters

KAELz4 asynchronous APIs support both polling and non-polling modes.
These APIs support three compression formats: block, frame, and lz77_raw. The block and frame formats are compatible with the standard LZ4 block and frame formats. The lz77_raw format needs to be converted to the standard block or frame format via a post-processing API.
The following describes the API combinations for different data formats in different polling modes.

```c
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <time.h>
#include <lz4.h>
#include <lz4frame.h>
#include <unistd.h>

#include <fcntl.h> // for O_RDONLY and open
#include <sys/mman.h> // for munmap
#include <inttypes.h>

#define HPAGE_SIZE (2 * 1024 * 1024) // 2-MB huge page
#define PAGE_SHIFT 12
#define PAGE_SIZE (1UL << PAGE_SHIFT)
#define PFN_MASK ((1UL << 55) - 1)

static int g_has_done = 0; // Whether the asynchronous callback is complete. The value needs to be initialized to 0.
static int g_file_chunk_size = 256;

struct my_custom_data {
    void *src;
    void *tuple;
    void *dst;
    struct kaelz4_buffer_list src_list;
    struct kaelz4_buffer_list tuple_list;
    struct kaelz4_buffer_list dst_list;
    void *src_decompd;
    size_t src_len;
    size_t dst_len;
    size_t src_decompd_len;
};
struct cache_page_map {
    uint64_t *entries;
    size_t entries_num;
    void *base_vaddr;
};

static struct cache_page_map* init_cache_page_map(void *base_vaddr, size_t total_size)
{
    struct cache_page_map *cache = malloc(sizeof(struct cache_page_map));
    if (!cache) return NULL;

    int fd = open("/proc/self/pagemap", O_RDONLY);
    if (fd < 0) {
        perror("Failed to open /proc/self/pagemap.");
        free(cache);
        return NULL;
    }

    // Calculate the number of entries to be read based on allocated size.
    size_t pages_num = total_size / PAGE_SIZE;
    cache->entries_num = pages_num;

    cache->base_vaddr = base_vaddr;

    // Allocate the cache space.
    cache->entries = malloc(pages_num * sizeof(uint64_t));
    if (!cache->entries) {
        close(fd);
        free(cache);
        return NULL;
    }

    // Calculate the file offset (the base address is the first entry, that is, the page corresponding to the allocated virtual address).
    uintptr_t base = (uintptr_t)base_vaddr;
    uintptr_t first_offset = (base / PAGE_SIZE) * sizeof(uint64_t);

    // Locate the start position.
    if (lseek(fd, first_offset, SEEK_SET) != first_offset) {
        perror("lseek failed.");
        close(fd);
        free(cache->entries);
        free(cache);
        return NULL;
    }

    // Read all entries applied for at this time.
    if (read(fd, cache->entries, pages_num * sizeof(uint64_t)) != (ssize_t)(pages_num * sizeof(uint64_t))) {
        perror("Entry read failed.");
        close(fd);
        free(cache->entries);
        free(cache);
        return NULL;
    }
    close(fd);
    return cache;
}

static void *get_huge_pages(size_t total_size)
{
    void *addr = mmap(
        NULL,
        total_size,
        PROT_READ | PROT_WRITE,
        MAP_PRIVATE | MAP_ANONYMOUS | MAP_HUGETLB,
        -1, 0
    ); // Apply for huge pages.

    if (addr == MAP_FAILED) {
        fprintf(stderr, "Failed to apply for huge pages.\n");
        fprintf(stderr, "The system may not have enough huge pages.\n");
        fprintf(stderr, "Try to allocate more huge pages: sudo sysctl vm.nr_hugepages=10000\n");
        exit(EXIT_FAILURE);
    }

    return addr;
}

static uint64_t get_physical_address_cache_page_map(struct cache_page_map *cache, void *vaddr) {
    uintptr_t virtual_addr = (uintptr_t)vaddr;

    // Calculate the entry index in the cache.
    uintptr_t base = (uintptr_t)cache->base_vaddr;
    uintptr_t index = (virtual_addr - base) / PAGE_SIZE;

    // printf("uintptr_t index = %ld . entries_num = %ld \n", index, cache->entries_num);
    if (index >= cache->entries_num) {
        fprintf(stderr, "The address is out of the cache range.\n");
        return 0;
    }

    uint64_t entry = cache->entries[index];

    if (!(entry & (1ULL << 63))) {
        fprintf(stderr, "The page does not exist.\n");
        return 0;
    }

    // Obtain the physical frame number (PFN).
    uint64_t pfn = entry & PFN_MASK;
    return (pfn << PAGE_SHIFT) | (virtual_addr & (PAGE_SIZE - 1));
}

static void* get_physical_address_wrapper(void *usr, void *vaddr, size_t sz)
{
    struct cache_page_map *cache = (struct cache_page_map *)usr;
    uint64_t phys_addr = get_physical_address_cache_page_map(cache, vaddr);
    return (void*)(uintptr_t)phys_addr;
}


static void *g_page_info = NULL;
static size_t read_inputFile(const char* fileName, void** input)
{
    FILE* sourceFile = fopen(fileName, "r");
    if (sourceFile == NULL) {
        fprintf(stderr, "%s not exist!\n", fileName);
        return 0;
    }
    int fd = fileno(sourceFile);
    struct stat fs;
    (void)fstat(fd, &fs);
    size_t input_size = fs.st_size;

    int huge_page_num = (int)(input_size * sizeof(Bytef) / HPAGE_SIZE) + 1; //Huge pages are 2 MB in size. Any requested allocation must be an integer multiple of this size.
    size_t total_size = huge_page_num * HPAGE_SIZE;
    *input = get_huge_pages(total_size);

    if (*input == NULL) {
        return 0;
    }
    (void)fread(*input, 1, input_size, sourceFile);

    struct cache_page_map* cache = init_cache_page_map(*input, total_size);

    // printf("Initialize data %ld \n", cache->entries_num);
    // uint64_t phys_addr = get_physical_address_cache_page_map(cache, *input);

    // printf("Huge page physical address: 0x%" PRIx64 "\n", phys_addr);
    g_page_info = cache;
    fclose(sourceFile);

    return input_size;
}

static void release_huge_pages(void *addr, size_t total_size)
{
    munmap(addr, total_size);
}
static int prepare_tuple_buf(void **tuple_buf, size_t src_len, struct cache_page_map** page_cache)
{
    size_t tuple_buf_len = KAELZ4_compress_get_tuple_buf_len(g_file_chunk_size * 1024) * (src_len / (g_file_chunk_size * 1024) + 1) * 2;
    size_t huge_page_num = tuple_buf_len * sizeof(Bytef) / HPAGE_SIZE + 1; // Huge pages are 2 MB in size. Any requested allocation must be an integer multiple of this size.
    size_t total_size = huge_page_num * HPAGE_SIZE;
    *tuple_buf = get_huge_pages(total_size);
    // printf("Virtual address of the allocated tuple buf huge page: %p len: 0x%lx\n", *tuple_buf, total_size);

    if (*tuple_buf == NULL) {
        return -1;
    }

    memset(*tuple_buf, 0, total_size);

    struct cache_page_map* cache = init_cache_page_map(*tuple_buf, total_size);
    if (cache == NULL) {
        printf("init_cache_page_map failed\n");
        return -1;
    }
    // uint64_t phys_addr = get_physical_address_cache_page_map(cache, *tuple_buf);
    // printf("tuple buf huge page physical address: 0x%" PRIx64 "\n", phys_addr);
    *page_cache = cache;

    return 0;
}

static void compression_callback3(struct kaelz4_result *result) {
    if (result->status != 0) {
        printf("Compression failed with status: %d\n", result->status);
        return;
    }
    // Obtain compressed data from the callback.
    struct my_custom_data *my_data = (struct my_custom_data *)result->user_data;

    if (KAELZ4_rebuild_lz77_to_block(&my_data->src_list, &my_data->tuple_list, &my_data->dst_list, result) != 0) {
        printf("[user]KAELZ4_rebuild_lz77_to_block : %d\n", result->status);
    }

    size_t compressed_size = result->dst_len;
    void *compressed_data = my_data->dst_list.buf[0].data;

    my_data->dst_len = compressed_size;

    // Decompress data using LZ4.
    size_t tmp_src_len = result->src_size * 10;
    // Allocate memory for decompressed data.
    void *dst_buffer = malloc(tmp_src_len);
    if (!dst_buffer) {
        printf("Memory allocation failed for decompressed data.\n");
        return;
    }

    size_t ret =  LZ4_decompress_safe((char *)compressed_data, (char *)dst_buffer, compressed_size, tmp_src_len);
    if (ret < 0) {
        printf("Decompression failed with error code: %ld\n", ret);
        free(dst_buffer);
        return;
    }
    tmp_src_len = ret; // Decompressed data length.
    my_data->src_decompd = dst_buffer;
    my_data->src_decompd_len = tmp_src_len;

    if (my_data->src_decompd_len != my_data->src_len) {
        printf("Test Error: The length after decompression is different from the original length. result->src_size=%ld   Original length=%ld   Length after decompression=%ld \n",
            result->src_size,
            my_data->src_len,
            my_data->src_decompd_len);
    }

    // Compare the decompressed data with the original data.
    if (memcmp(my_data->src_decompd, my_data->src_list.buf[0].data, result->src_size) == 0) {
        printf("Test Success.\n");
    } else {
        printf("Test Error:Decompressed data does not match the original data.\n");
    }

    // Release decompressed data.
    free(dst_buffer);
    g_has_done = 1;
}

    return compression_status;
}
```

## 6. Performance Optimization

* Adjusting the number of concurrent KAE threads: The number of concurrent threads affects the compression efficiency. Too many threads consume more KAE queue resources. It is recommended that a single compression process starts 12 concurrent threads to achieve good bandwidth performance.

    ~~~shell
    # KAE_LZ4_ASYNC_THREAD_NUM: number of concurrent threads that can be started by a single process on the KAE side.
    # By default, 12 threads are started to concurrently process compression tasks. A maximum of 32 threads can be started. 
    export KAE_LZ4_ASYNC_THREAD_NUM=12
    ~~~

* Core binding description:
  * You can use taskset or numactl to bind the compression process to cores and restrict the use of hardware accelerators.
  * Generally, at least **KAE\_LZ4\_ASYNC\_THREAD\_NUM** CPUs must be bound to KAE for compression. Considering the user-side logic, at least **KAE\_LZ4\_ASYNC\_THREAD\_NUM** plus 1 CPU cores must be bound.
  * By default, KAE concurrent threads automatically select the hardware accelerators on the NUMA node where the process is located and the adjacent NUMA node to achieve the maximum bandwidth.
  * If you want to use only one accelerator, bind the compression process to the CPU core of a single NUMA node.
  * On a VM with hyper-threading enabled, two consecutive CPU cores are usually from the same physical core. In this case, you need to bind non-contiguous cores or bind more CPU cores to achieve the maximum bandwidth.

## 7. FAQs

### 1. Does the kzip tool support multi-process concurrency?

Yes.
When using Lz4 for testing the KAELz4 synchronous APIs for compressing data in the block or frame format, you can use the **-m** parameter to specify the number of concurrent processes for the pressure test.
In tests with KAELz4 asynchronous APIs for compressing data in the block or frame format, a single process can fully use the bandwidth. Multiple processes do not add more benefits.
To simulate multi-process asynchronous compression, you can use the **-i** parameter of the tool. Set `inflight_num` between 1 and 1024 to control the number of concurrent KAE asynchronous compression API tasks in a process. If the limit is reached, the API can be called to execute a new compression task only after the previous one completes and its callback function runs. This controls the compression traffic on the user side. The default value is 256, which indicates high compression traffic.
